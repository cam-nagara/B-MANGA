## 1. チャットで合意した成果・負担・期限

### 1.1 成果

B-MANGA本体について、現在のUI、操作感、見た目、用語、ショートカットを意図せず変更せず、画面から利用できる機能を微細挙動、保存・再読込、Undo/Redo、失敗復旧、基本書き出しまで検証し、確認した不具合を修正する。

目的は計画上の新アーキテクチャを完成させることではない。ユーザーが実制作を開始でき、同種の不具合を決定的な回帰テストで再発検知できるB-MANGA本体の安定版候補を作ることである。

非自明なソフトウェアについて「将来の不具合が一切ない」とは保証しない。合格時は、確認できた範囲、未確認と理由、残るリスクを区別して報告する。

### 1.2 期間

- 連続実行で**5〜7暦日**を目標とする。2026-08-08開始なら目標日は2026-08-15まで。
- 時間を守るため、B-MANGA Render / Linerの機能認定、根拠のない全面置換、独立目的のファイル分割、重複するfull test、複数GPU、人間QA 2名、5営業日・20時間soakは行わない。
- Day 7時点でin-scopeの重大不具合が残る場合、合格を偽らず、再現条件、影響、残作業をチャットで直接報告する。仕様変更または外部協力が不要な通常の修正は確認待ちで止めず続ける。

### 1.3 ユーザー負担

- 実装中のテスト、Blender操作、成果物再読込、レビューはAIが行う。
- 独立した人間テスターや別GPU環境をユーザーに用意させない。
- 通常版への配備前に、必要な場合だけ15〜30分程度の最終的な見た目・描き味確認を1回に集約する。ユーザーをデバッグ要員にはしない。

### 1.4 データと通常環境への影響

- Nextは実作品制作前の一回限りのclean breakとして、旧作品・旧保存形式の自動互換を持たない。保存失敗、強制終了、遷移失敗の復旧安全は維持する。
- ユーザーが現在使う通常Extension `b_manga` v0.6.599へ、中間版を配備しない。
- Nextは別Extension ID `b_manga_next`のまま検証する。push、tag、公開、通常環境への配備は、この計画の実行だけでは行わない。

### 1.5 最小案との違い

最小案はmain v0.6.599へ判明済み不具合だけを個別修正する1〜3日程度の作業である。ただし、保存・移送・UI配線の横断回帰と既に作成済みのNext基盤を活用できない。本計画は一週間枠の中で、既存Next成果を監査して活用し、本体の横断的な再発防止まで行う。

## 5. 検証とレビューの原則

1. 実装分岐と変更影響から対象テストを先に選ぶ。
2. 修正前に再現できる不具合は、修正後に通る決定的回帰テストへ固定する。
3. 各Phaseは対象unit / contract / Blender実機 / 必要なheaded UI・画像比較で判定する。
4. 同じケースを含むfull suiteを小修正ごとに重ねない。全コード安定後にB-MANGA本体対象のfull suiteを1回実行する。
5. 独立レビューは差分が安定した時点で読取専用として行い、同じ差分への重複レビューをしない。重大・高指摘を修正した場合は対象再検証後、最終full suiteを再実行する。
6. 対象変更と無関係な既存P2、style、文書改善、全面分割は、合否根拠を無効化しない限りAGENT_INBOXへ分離する。
7. 再現可能なin-scopeのユーザー機能不具合は重要度にかかわらず放置して合格にしない。重大・高、データ損失、テスト判定を無効化する問題は必ずPhaseをブロックする。
8. 各コード変更Phaseは、対象検証、独立レビューが必要な場合の重大・高0、再検証を満たしてから個別コミットする。pushと通常配備はしない。

## 7. 停止条件

次の場合だけユーザー判断のため停止する。

- UI、操作、見た目、用語、保存形式について複数の妥当な仕様があり、選択が結果を変える。
- B-MANGA Render / LinerまたはMeldex側の仕様変更・実装協力が必要になる。
- 通常Extensionへの配備、push、tag、公開、実データ移行など新しい権限が必要になる。
- ユーザーの実作品または設定へ不可逆な変更が必要になる。

通常のテスト失敗、内部設計判断、実装上の難しさ、時間の経過だけでは停止しない。最小の安全な修正を選び、Phaseの合格条件を満たすまで続ける。
